# v0.4 Read-only Project Resume — Acceptance Tests

| Field | Value |
|---|---|
| Status | Accepted |
| Owner | Chief Architect / CTO |
| Release | v0.4 |
| Prerequisite | v0.3.1 Query Trust Contracts accepted and released |
| Pilot projects | AI Operating System; Cloud Organizer Pro |

## Release outcome

A user selects one project and receives a sourced, read-only briefing that makes it
faster to resume meaningful work. The user can inspect why each material statement
appears and can correct bad context without Jarvis writing to the vault.

## Acceptance scenarios

### A1 — Exact project selection

Given a unique canonical project identity, the briefing selects only that project and
reports objective, current status, priorities, accepted decisions, recent sessions,
open tasks/questions, resources, repository activity when authorized, and missing
context. Every material statement has a passage-and-revision citation.

### A2 — Ambiguous and missing identity

When aliases or titles match multiple projects, Jarvis presents the safe candidates and
does not choose. When none match, it reports not found and does not substitute a related
project.

### A3 — Authorization and sensitivity

A note outside the request scope or above the sensitivity ceiling cannot influence
selection, ranking, graph expansion, briefing text, citations, conflicts, or trace.
Repository activity is absent unless its read scope is explicitly granted.

### A4 — Current-state ordering

Accepted decisions outrank draft discussion. Current authoritative project state outranks
older session summaries. Material conflicts and staleness are shown rather than silently
resolved.

### A5 — Citation inspection

Every citation opens or resolves to the exact source revision and supporting passage.
Changed, deleted, or unavailable sources are marked stale/unavailable; the claim is not
presented as verified.

### A6 — Context budget

The briefing remains within its configured context and output budgets. Oversized project
notes, cycles, and large linked collections terminate deterministically and report
omissions.

### A7 — Read-only integrity

Before/after inventories prove no source files, metadata, repository state, external
resources, or durable conversation state changed. Output is ephemeral or written only
to an explicitly authorized non-vault destination.

### A8 — Determinism and trace

For the same source snapshot, authorization scope, request, and configuration, structured
selection and citations are byte-identical. Trace includes request ID, vault fingerprint,
contract/index versions, safe policy summary, selected sources, omissions, and timings.

### A9 — Degraded dependencies

Unavailable GitHub or resource links produce a partial briefing with a clear limitation.
Local vault evidence remains usable. No retry loop or external failure prevents safe local
completion.

### A10 — Performance

The briefing completes in under 30 seconds for each pilot vault on documented reference
hardware. Retrieval-stage p50/p95/p99 and total latency are recorded separately.

### A11 — User value

During an eight-week dogfood period, record each meaningful project-resume attempt:

- successful/abandoned;
- time to useful orientation;
- estimated time saved;
- incorrect or missing context;
- citation defects;
- correction/metadata time;
- requested features.

At least 80% of rated briefings must be useful before advancing. The strategic validation
target is 15–30 minutes saved per meaningful project switch and 90–95% correctly sourced
material claims.

### A12 — Packaging and recovery

A non-author follows the installation and diagnostic documentation on a clean supported
environment, runs both pilot briefings, rebuilds derived state, and recovers from a
corrupt/missing index without changing canonical sources.

## Automated evidence matrix

| Test class | Minimum evidence |
|---|---|
| Unit | identity, authority ordering, staleness, scope, budget, passage validation |
| Fixture | exact, ambiguous, missing, conflicting, restricted, oversized, cyclic projects |
| Integration | CLI Project Resume, repository degradation, trace, unchanged-vault checks |
| Compatibility | v0.3.1 contract fixtures and supported CLI behavior |
| Security | scope bypass, path traversal, prompt injection as data, trace/error disclosure |
| Performance | pilot and synthetic vault p50/p95/p99 with source counts |
| Human evaluation | claim-level citation review and weekly dogfood scorecard |

## Release exclusions

v0.4 does not include visible-context chat, real provider generation, durable conversation
storage, proposed memory, writes, plugins, MCP, agents, or automation. Any proposal to add
one of these requires Product Owner re-scoping and its applicable security/release gates.

## Release gate

Quality & Release independently executes the matrix and issues one disposition: Ready,
Ready with conditions, Refactor first, Not ready, or Re-scope. Jason makes the final
release decision.
