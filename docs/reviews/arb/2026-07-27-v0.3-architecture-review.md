## Executive decision

**Outcome: Ready with conditions.**

v0.3 is a sound read-only query foundation and is ready to support the next **read-only Project Resume pilot**. It is **not yet approved for real AI providers, sensitivity-bearing multi-user data, durable memory, plugins, MCP tools, or automation**.

The implementation preserves the central architectural decisions: local-first operation, read-only behavior, provider abstraction, deterministic lexical retrieval, explicit citations, and a layered pipeline. It also introduces appropriate seams without adding a database, vector store, background service, or framework prematurely.

The primary concerns are trust semantics rather than module structure:

1. the field named `confidence` represents relative retrieval score, not answer confidence;
2. citation records identify notes but not the passages supporting claims;
3. retrieval does not yet enforce sensitivity or authorization scope;
4. the context builder's documented token-budget guarantee is not strict for an oversized first chunk;
5. v0.3 delivers the query/provenance portion of the roadmap milestone, not the entire chat/provider milestone.

These do not invalidate the merged query foundation. They must be resolved before the system presents generated answers from real providers.

## Review scope and evidence

The review examined:

- the v0.3 implementation report and benchmark table;
- ADR-0012 and query documentation;
- the query engine, index, intent parser, ranker, context builder, result, and trace contracts;
- the CLI surface and associated test inventory;
- the merge history and reported 124-test, Ruff, and mypy results;
- applicable system principles, behavior rules, PRDs, security model, and ADRs.

Independent local execution was attempted. The repository virtual environment could not be executed from the review sandbox, so the reported 124-test result was not independently reproduced during this review. This is an evidence limitation, not a failed test.

## Strengths

### Layered but restrained design

`IntentParser`, `LexicalIndex`, `Ranker`, `QueryContextBuilder`, and `QueryEngine` have distinct reasons to change. Constructor injection makes ranking and provider behavior replaceable without introducing a dependency-injection framework.

### Explainable lexical baseline

Field-specific weights, stable tie-breaking, and signal-level ranking explanations establish a transparent baseline. Future semantic retrieval can be evaluated against it rather than replacing an unknown heuristic.

### Derived-state discipline

The index is rebuildable and in memory. This respects the canonical/derived/operational storage separation and avoids premature persistence concerns.

### Useful trace foundation

The trace captures parsed intent, candidates, ranking, exclusions, context, provider, timing, and token estimates. It protects debuggability before provider complexity arrives.

### Compatibility was handled intentionally

The old `ask()` contract remains available while the richer query surface is introduced. The debt is acknowledged rather than hidden.

### Performance is appropriate for the current target

Reported median construction-plus-query time is 42.81 ms at 1,000 notes, with approximately linear behavior from 100 to 1,000 notes. This is sufficient evidence for the present pilot, though not evidence for million-note scale.

## Required conditions

### C1 — Separate retrieval relevance from answer confidence

**Priority:** Required before real-provider answers
**Owner:** Query Engine engineer
**Gate:** Real provider or conversational answer integration

`ScoredNote.confidence` is `score / top_score`; the highest result therefore receives `1.0` even when all evidence is weak. This is a useful relative-relevance value but conflicts with the AI Behavior Standard's calibrated confidence semantics.

Required change:

- rename the retrieval field to `relative_relevance`, `rank_score_normalized`, or equivalent;
- reserve `answer_confidence` for evidence sufficiency, agreement, freshness, ambiguity, and coverage;
- version the serialized result contract or provide a compatibility alias with a deprecation plan;
- update CLI language and documentation so users do not interpret rank as truth probability.

### C2 — Make the context budget a true invariant

**Priority:** Required before passing context to real providers
**Owner:** Query Engine engineer
**Gate:** Real provider integration

`QueryContextBuilder` admits the first planned chunk even when it exceeds the configured budget because exclusion only occurs when `included` is already non-empty. The associated test assertion does not verify the invariant: `total_tokens <= max(total_tokens, 1)` is always true.

Required change:

- define explicit oversized-seed behavior: truncate, exclude with a structured error, or admit under a separately named hard-cap exception;
- enforce `total_tokens <= token_budget` when the contract calls the budget hard;
- replace the tautological test with assertions against the declared behavior;
- test zero, negative, tiny, exact-boundary, and oversized-first-note budgets.

### C3 — Add claim-supporting citation anchors

**Priority:** Required before generated prose is represented as evidence-backed
**Owner:** Query and provider engineers
**Gate:** Real provider or chat release

Current citations contain note ID, title, path, relative relevance, and selection reason. They show why a note was retrieved, not which passage supports a claim.

Required change:

- add stable section/block or character-range anchors where feasible;
- include a short supporting excerpt and source revision/fingerprint;
- map generated claims to one or more citation IDs;
- validate that cited passages exist in the indexed source version;
- suppress or label claims that fail citation validation.

### C4 — Enforce sensitivity and authorization before retrieval

**Priority:** Blocking for cloud providers, multi-user use, plugins, MCP, and agents
**Owner:** Security architecture and Query Engine engineer
**Gate:** Any non-mock provider or expanded trust boundary

Sensitivity-scoped retrieval is explicitly deferred. That is acceptable for a private, offline, single-user pilot, but filtering after context assembly is too late: restricted content may already have entered a prompt or trace.

Required change:

- introduce a request scope containing identity, project/workspace, allowed sources, and sensitivity ceiling;
- filter candidate generation and graph expansion before ranking/context assembly;
- ensure trace and error messages observe the same scope;
- add negative tests proving unauthorized notes cannot appear as candidates, neighbors, citations, excerpts, or diagnostics.

### C5 — Reconcile release naming and completion criteria

**Priority:** Required before declaring the full v0.3 milestone complete
**Owner:** Product owner
**Gate:** Version status update

ADR-0012 correctly documents that chat, conversation storage, and real provider adapters remain deferred. Product reporting should call the merged feature the **v0.3 Query Engine foundation** or update the roadmap acceptance criteria. It should not imply that the full “Read-only Chat and Provenance” milestone is complete.

Required change:

- record which original v0.3 acceptance criteria are complete, deferred, or moved;
- decide whether remaining chat/provider work stays in v0.3.x or moves to a later version;
- keep one release-status source of truth.

## Recommended non-blocking refactors

| Recommendation | Timing | Reason |
|---|---|---|
| Add a `Retriever` port | Before persisted, hybrid, or authorization-aware retrieval | Prevent candidate generation from becoming coupled to `LexicalIndex` |
| Precompute incoming/outgoing adjacency maps | Before relationship-heavy Project Resume | Avoid repeated edge scans and centralize graph traversal |
| Make legacy `ask()` a thin adapter over one canonical result contract | Before public API stabilization | Retire dual-surface behavior without breaking current callers |
| Add request ID, vault fingerprint, index version, policy decision, and template/provider version to trace | Before provider integration | Make results reproducible and operationally auditable |
| Separate “selection reason” from “evidence reason” | With citation-anchor work | A ranking signal is not proof of a claim |
| Replace default empty graph expansion with explicit depth/edge policy | Before relationship discovery | Prevent context growth and make traversal semantics testable |
| Introduce benchmark budgets by stage at 10k and 100k synthetic notes | Before persisted index work | Choose storage optimization from measured thresholds |

## Complexity and technical debt

The present module count is justified; no material over-engineering was found. The main debt items are correctly identified in the implementation report:

- dual answer surfaces;
- zero-score graph-selected leftovers mixed into relevance ordering;
- per-instance index rebuild;
- graph APIs that encourage repeated edge scans.

One additional debt item should be tracked: **the same `confidence` term is being used for retrieval rank and user trust.** This is more dangerous than a naming detail because it will propagate into APIs, UI, benchmarks, and user expectations.

The zero-score leftovers should eventually be represented as a separate relationship-derived result group or carry a typed selection channel. Appending them to a relevance-ranked list makes ordering deterministic but semantically heterogeneous.

## Security and privacy review

For the current offline, single-user, mock-provider scope, the read-only posture is preserved. No new secrets or network path were added.

Security approval does not extend beyond that scope. Before real providers or tools:

- authorization must constrain retrieval before context construction;
- retrieved Markdown must be treated as untrusted content;
- trace output must not leak excluded or sensitive note names;
- provider adapters require egress and data-handling policy;
- prompt-injection tests must demonstrate that note content cannot change policy or grant tools.

## Performance and operability

The benchmark supports the current 1,000-note pilot. It does not validate the strategic aspiration of millions of notes, which should remain a future constraint rather than a present acceptance requirement.

Before using performance results for architecture selection:

- report p50/p95/p99, not median only;
- distinguish cold construction, warm query, and provider latency;
- include dense-link graphs, long notes, common-term queries, and worst-case candidate sets;
- capture peak memory and index size;
- measure the actual pilot vault in addition to synthetic fixtures.

The current trace is a good diagnostic baseline. Request identity, vault/index fingerprints, configuration versions, and failure/retry events will be required as the pipeline becomes distributed or provider-backed.

## Final recommendation

Accept the merged implementation as the **v0.3 Query Engine foundation**. Authorize the next read-only vertical slice—Project Resume—while opening C1 through C5 as explicit tracked work. Do not enable real-provider synthesis merely because a `Provider` interface exists; the evidence, confidence, budget, and authorization contracts must be hardened first.

After the next material Claude implementation, provide its implementation report, changed contracts, benchmark results, security analysis, and unresolved debt for the next Architecture Review Board review.
