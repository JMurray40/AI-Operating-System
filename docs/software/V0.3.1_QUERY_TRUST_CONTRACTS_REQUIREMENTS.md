# v0.3.1 Query Trust Contracts — Implementation Requirements

| Field | Value |
|---|---|
| Status | Accepted |
| Owner | Chief Architect / CTO |
| Release | v0.3.1 |
| Scope | Offline, local, read-only query trust hardening |
| Depends on | ADR-0007, ADR-0012, AI Behavior Standard, v0.3 ARB review |
| Excludes | Chat, real providers, embeddings, writes, plugins, MCP, agents, automation, watchers |

## Objective

Close Architecture Review Board conditions C1 through C5 before any generated-answer,
real-provider, or expanded-trust-boundary work. The release must make retrieval,
authorization, context budgeting, citations, identity, and trace behavior explicit,
versioned, deterministic, and testable.

This release does not make Jarvis conversational. It produces trustworthy query
contracts on which Project Resume and later visible-context chat may safely depend.

## Required contract changes

### R1 — Retrieval relevance and answer confidence

1. Rename ranking and citation fields named `confidence` to `relative_relevance`.
2. Define relative relevance as a deterministic ranking normalization within one result
   set. It is not a probability, correctness claim, or comparison across queries.
3. Do not expose numeric answer confidence in v0.3.1.
4. Reserve an `answer_confidence` field for a later evidence assessment contract. If
   present for compatibility, it must be null and documented as unavailable.
5. User-visible text and Trace Mode must use the terms **relative relevance** and
   **answer confidence** only with these meanings.

### R2 — Strict context budget invariant

1. `used_tokens` must never exceed `token_budget`.
2. The budget must include every emitted chunk and all deterministic separators or
   wrapper overhead counted by the context contract.
3. An oversized first note must be truncated to a deterministic, non-negative allowance
   or omitted with an explicit reason; it must never be admitted whole.
4. A zero budget must produce no content chunks.
5. Negative budgets must fail validation before retrieval.
6. Trace Mode must report budget, used tokens, omitted/truncated sources, and reason.

### R3 — Passage and revision citation contract

Every citation emitted for an answer or context package must contain:

- stable `source_id`;
- source relative path for human inspection;
- source title;
- source fingerprint representing the exact bytes parsed;
- a deterministic locator: heading path plus line range or another documented passage
  identifier;
- a bounded excerpt copied from that passage;
- `relative_relevance` when the citation originated from ranked retrieval;
- retrieval reason.

The system must verify that the locator resolves against the cited fingerprint and that
the excerpt occurs in the resolved passage. A note-level citation without a supporting
passage is not sufficient for a material claim.

### R4 — Authorization before candidate generation

Introduce an immutable `AuthorizationScope` supplied to every query entry point. At
minimum it contains:

- workspace identifier;
- allowed source identifiers or path prefixes;
- maximum sensitivity;
- allowed note types, when restricted;
- purpose/request identifier for trace correlation.

The scope must be applied during source discovery or before index candidate generation.
Unauthorized notes must not enter:

- the lexical index visible to the request;
- candidate or ranking collections;
- graph seed or expansion collections;
- context chunks;
- citations;
- conflict detection;
- user-visible errors;
- Trace Mode, except for aggregate exclusion counts that reveal no identity.

Unknown scope, unknown sensitivity, or missing workspace identity fails closed.

### R5 — Stable identity and source revision

1. `source_id` must be stable across title, alias, and path changes where an explicit
   canonical ID exists.
2. When no canonical ID exists, derive a documented workspace-scoped ID and label it as
   path-derived.
3. `source_fingerprint` must change when source bytes change and remain stable when they
   do not.
4. Entity identity and source revision must remain separate concepts.
5. Duplicate canonical IDs are validation errors and must not be silently merged.

### R6 — Versioned results and trace

1. Add an explicit contract version to structured query results, citations, context
   packages, and traces affected by this release.
2. New JSON output uses the v0.3.1 names.
3. A single-release compatibility reader may accept legacy `confidence`; writers must not
   emit both names as if they had different meanings.
4. Text output must use the new terminology.
5. Trace adds request ID, workspace/vault fingerprint, index version, contract version,
   authorization decision summary, and provider/prompt version when applicable.

### R7 — Roadmap and milestone documentation

Document v0.3 as the Query Engine foundation and v0.3.1 as trust-contract hardening.
Project Resume is the proposed v0.4 release. Visible-context chat is proposed for v0.5,
subject to Product Owner approval. No conversation branch may redefine the release
sequence implicitly.

## Acceptance matrix

| Area | Required evidence |
|---|---|
| Relevance | No affected public or text contract labels retrieval ranking as confidence |
| Answer confidence | No numeric answer-confidence claim is produced in v0.3.1 |
| Budget | Property/boundary tests prove `0 <= used_tokens <= token_budget` |
| Oversized source | First and later oversized notes truncate/omit deterministically |
| Citation | Locator, excerpt, and fingerprint resolve to the exact parsed source |
| Stale citation | Changed source fingerprint causes validation failure, not silent reuse |
| Authorization | Excluded note cannot affect ranking, graph expansion, context, citations, conflicts, or trace |
| Fail closed | Missing/invalid workspace or sensitivity scope returns a typed policy error |
| Identity | Rename behavior, path-derived fallback, and duplicate canonical ID are tested |
| Compatibility | Legacy reader fixture and new writer snapshot are tested |
| Determinism | Identical snapshot, scope, query, and config produce byte-identical structured output |
| Read-only | Before/after file inventory, content hashes, and metadata remain unchanged |
| Regression | Existing supported v0.1–v0.3 commands retain documented behavior |
| Quality | Full tests, Ruff, and mypy pass |
| Performance | 1,000-note p95 does not regress by more than 20% from the accepted baseline |

Tests must include positive, negative, boundary, compatibility, security, and regression
cases. An implementation report must map every requirement and test to changed code.

## Security implications

This release narrows the read trust boundary. Authorization filtering must be structural,
not a post-retrieval redaction step. Traces and error messages are output channels and
must receive the same non-disclosure treatment as answers. Source fingerprints are
integrity identifiers, not secrets; excerpts may be sensitive and therefore inherit the
source sensitivity.

No real provider may be introduced by this release. Provider egress remains blocked until
scope enforcement, context preview, secrets handling, and prompt-injection controls pass
their separate release gates.

## Migration and compatibility

This is a pre-1.0 contract correction. Prefer one clean breaking change over preserving
ambiguous semantics indefinitely.

1. Publish old-to-new field mapping in the implementation report.
2. Accept legacy serialized fixtures only at an explicit compatibility boundary.
3. Emit only the new contract.
4. Mark compatibility parsing for removal no earlier than the next minor release.
5. Do not reinterpret stored numeric `confidence` as answer confidence.

## Implementation sequence

1. Add identity, revision, authorization, and versioned contract types.
2. Filter authorized sources before index construction/candidate generation.
3. Correct relevance terminology.
4. enforce the context-budget invariant.
5. Build and validate passage citations.
6. Extend Trace Mode without disclosing excluded identities.
7. Add compatibility readers and migration documentation.
8. Execute the complete acceptance matrix and benchmark.

## Release evidence package

Engineering must submit:

- implementation report and requirement-to-test matrix;
- changed public contracts and compatibility notes;
- full automated and static-check results;
- benchmark method, hardware, raw result summary, p50/p95/p99;
- authorization and citation adversarial results;
- unchanged-vault evidence;
- security analysis, technical debt, and deviations.

Quality & Release then performs an independent review. Jason retains final approval.
