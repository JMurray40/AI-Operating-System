## Mission

Transform Jarvis from a vault-inspection tool into an intelligent **read-only** query
engine that answers questions about an Obsidian vault while preserving every architectural
principle from v0.1/v0.2. No write capability was introduced.

## What shipped

A dedicated query layer (`jarvis_core.query`) composed of small, injected collaborators,
plus four query commands and a trace mode:

- **Query layer** — `tokenizer`, `LexicalIndex`, `IntentParser`, `Ranker`,
  `QueryContextBuilder`, `results` (citations), `trace`, orchestrated by `QueryEngine`.
- **Lexical search** — inverted index over title, aliases, tags, filename, frontmatter,
  wikilinks, and body. No embeddings, no vectors, no semantic search, no vector DB.
- **Deterministic, explainable ranking** — configurable `RankingWeights`; every hit
  carries per-signal contributions and a confidence relative to the top hit; ties break on
  relative path.
- **Context builder** — token-budgeted expansion of ranked seeds along the resolved graph
  into a provider-independent `QueryContext` (with an explicit excluded list).
- **Provider integration** — only through the existing `Provider` abstraction
  (`MockProvider`); no provider-specific code in query logic.
- **Source citations** — every answer identifies source note, relative path, confidence,
  and reason.
- **Trace mode** — `jarvis ask "…" --trace` shows query, matched notes, ranking
  explanation, context selected, excluded notes, provider, timing, and token counts.
- **CLI** — `ask` (+`--trace`), `search`, `summarize`, `explain`, consistent with the
  existing command style and exit-code contract.

Backwards compatibility: the v0.2 `QueryEngine.ask()` / `QueryResult` surface is preserved;
all pre-existing tests pass unchanged.

- **124 tests pass** (55 added on top of the 69-test v0.2 baseline). `ruff` and `mypy
  --strict`-style config both clean.
- New coverage: tokenizer, index, intent parsing, ranking (exact/alias/tag/title/body,
  duplicate-title tie-breaks, custom weights, confidence), context builder (budget
  overflow, determinism), engine edge cases (alias-only, tag-only, missing frontmatter,
  broken wikilinks, empty results, ambiguous/graph-via-linked-note), explain, trace, CLI
  commands, and performance guardrails.
- Edge cases exercised per the brief: exact matches, partial matches, aliases, tags,
  broken links, missing frontmatter, duplicate titles, large vaults, ambiguous queries,
  empty results, and performance regression.

## Benchmark results

Median of 7 runs per size on the development sandbox (`scripts/benchmark_query.py`), in
milliseconds. Stages: `index_build` (one-time construction: index + graph resolution),
`retrieval` (candidate lookup), `ranking`, `context` (assembly), `provider(mock)`
(summarize path), and `total(query)` (index build + retrieval + ranking + context).

| notes | index_build | retrieval | ranking | context | provider(mock) | total(query) |
|---|---|---|---|---|---|---|
| 100 | 1.95 | 0.08 | 0.68 | 0.10 | 0.48 | 2.82 |
| 500 | 11.59 | 0.45 | 3.98 | 0.27 | 2.99 | 15.61 |
| 1000 | 31.16 | 0.83 | 10.997 | 0.70 | 6.57 | 42.81 |

Scaling is approximately linear across 100 → 1,000 notes. Retrieval grows ~linearly with
candidate count; ranking was made linear by precomputing backlink counts once (see the
technical-debt note below). A single query over a 1,000-note vault completes in well under
100 ms; the scale test enforces a <1 s ceiling as a regression guard.

## Engineering Review

*(Standard section carried in every implementation report so the architectural history
accumulates as Jarvis moves toward v1.0.)*

### 1. What architectural assumptions were made?

- The parsed `Note` set fits comfortably in memory, so an in-memory index rebuilt per run
  is acceptable at v0.3 sizes — no persisted or incremental index is needed yet.
- Lexical, deterministic retrieval is sufficient for v0.3; semantic similarity is out of
  scope, so tokenization can be a pure function with no stemming/synonyms.
- The v0.2 `ask()`/`QueryResult` contract must remain stable; new capability is added
  beside it, not by breaking it.
- Providers are reached only through the existing `Provider` abstraction; the engine never
  needs provider-specific behaviour.
- A word-count token estimate is good enough for budgeting; exact tokenization is a
  provider adapter's concern.
- `projects_mentioning` and `related_to` keep their v0.2 graph-aware *selection*; the
  ranker adds *ordering and explanation* on top rather than changing what is selected.

### 2. What technical debt was introduced (if any)?

- **Two answer surfaces coexist.** `QueryEngine.ask()` (legacy `QueryResult`) and the v0.3
  `run()/search()/summarize()/explain()` (cited `QueryAnswer`) both live on the engine.
  Intentional for compatibility, but the legacy surface should eventually be expressed as
  a thin adapter over the rich one.
- **`_rank_subset` appends zero-score leftovers.** Notes selected via a linked note (not
  their own text) are appended with zero confidence to preserve v0.2 selection semantics.
  It works and is deterministic, but it mixes two ranking philosophies in one list.
- **Index is rebuilt every invocation.** Fine now; a persisted/incremental projection is
  the obvious next optimization (already anticipated by the Search PRD).
- **Ranking backlink counting** originally called `ResolutionReport.incoming()` per
  candidate (O(candidates × edges), quadratic on dense vaults). Fixed by precomputing a
  backlink-count map once in the `Ranker`; noted here because the underlying
  `ResolutionReport.incoming/outgoing` scan-all-edges API invites the same mistake
  elsewhere.

### 3. What should be refactored before the next major release?

- Give `ResolutionReport` precomputed adjacency maps (out/in) so callers stop re-scanning
  all edges; migrate existing O(E)-per-call sites.
- Collapse the legacy `ask()` into an adapter over `run()` once no caller depends on the
  exact `QueryResult` ordering, removing the dual-surface debt.
- Extract a `Retriever` port (candidate generation) so the future persisted/hybrid index
  can be swapped in behind the same seam the Search PRD describes.

### 4. What work was intentionally deferred?

- The v0.3 roadmap's **conversational chat UI, conversation store, and cloud/Ollama
  provider adapters** (see ADR-0012 "Roadmap reconciliation"). This build delivered the
  query-engine and provenance half of the milestone.
- Embeddings / semantic (hybrid) ranking, persisted and incremental indexes, background
  file watching, and sensitivity-scoped retrieval — all explicitly out of scope per the
  brief and deferred to later versions.
- Any write capability — permanently out of scope for this milestone (ADR-0007).

### 5. If starting over today, what would be designed differently?

- Introduce the `Retriever`/`Ranker`/`ContextBuilder` ports **before** writing the v0.2
  `ask` prototype, so there would be a single answer surface from day one instead of a
  legacy path to preserve.
- Model the graph with adjacency maps from the start, avoiding the scan-all-edges API that
  produced a quadratic ranking path.
- Represent field weights and confidence bucketing in a small config object surfaced to
  the CLI, so ranking is tunable without code changes — the current `RankingWeights` is
  close but not yet CLI-exposed.
