## Mission

Turn the v0.3 query engine into a conversational knowledge assistant — multi-turn
follow-ups that understand context — while preserving every architectural principle so far.
Jarvis remains completely read-only: no vault modification, no autonomous actions, no
agents, no persistent memory.

*(This report follows the standard Engineering Review format defined in
[Ways of Working](../WAYS_OF_WORKING.md).)*

## Implemented

- **Conversation layer** (`jarvis_core.conversation`), composed over the query engine with
  state isolated from retrieval: `ConversationSession` (in-memory turns + entity stack +
  token-budgeted history), `ReferenceResolver` (deterministic pronoun/ellipsis resolution),
  `explanation` (statement taxonomy), `results.ConversationAnswer` + `StreamEvent`,
  `ConversationTrace`, and `ConversationManager`.
- **Multi-turn context**: pronouns/ellipsis resolve to the in-focus entity; each resolution
  is surfaced as a visible assumption; unrelated recent topics flag ambiguity.
- **Provenance on every answer**: reasoning summary, confidence, an explicit
  fact / inference / relationship / unknown / assumption basis, cited sources, and
  conflicting-evidence detection (shared title or duplicate id across notes).
- **Optional streaming** via a `SupportsStreaming` provider capability (base `Provider`
  contract unchanged); normalized events `started/delta/citation/usage/completed/failed`.
- **Graceful provider failure**: a failed provider yields a `failed` answer/event with no
  fabricated partial; the vault is untouched.
- **CLI `jarvis chat`**: scripted `--turns` (deterministic), interactive stdin with
  `:history`/`:reset`/`:trace`/`:help`/`:exit`, plus `--trace` and `--stream`.
- **Benchmarks & tests**: `scripts/benchmark_conversation.py`; scale tests at
  100/500/1,000/5,000 notes; 32 new tests (156 total). Read-only safety test extended to a
  chat run.

## Deferred

- Persistent/durable memory and conversation logs — remain separate future scope, kept out
  deliberately (ADR-0013).
- Real cloud/Ollama streaming provider adapters — the abstraction and mock streaming are in
  place; concrete adapters are a later milestone.
- Semantic/synonym understanding of follow-ups — retrieval stays lexical (v0.6 semantic).
- Conversation resume across processes (would require persistence).

## Tradeoffs

- **Session-only memory**: lost when the process ends. Buys zero persistence risk and keeps
  the read-only guarantee absolute.
- **Heuristic reference resolution** (most-recent focus + token-overlap ambiguity): simple
  and deterministic, but exotic anaphora may resolve imperfectly — always visibly, as a
  stated assumption.
- **Two answer surfaces** (`QueryAnswer`, `ConversationAnswer`): the conversational one
  wraps the query one rather than replacing it — a little duplication for a clean seam.

## Technical debt

- The manager appends the focus title to the raw query as the "effective query"; this
  anchors retrieval well but is a lexical shim, not true query rewriting. A structured
  query object would be cleaner and is the natural v0.6 refactor.
- `_build_statements` concentrates several small heuristics (fact phrasing, unknown
  detection); as taxonomy rules grow, extract a `ProvenanceBuilder` with per-rule units.
- `ask_stream` re-runs `ask()` internally; fine for the mock, but a real streaming provider
  should push deltas from the provider stream rather than re-chunking the final text.

## Performance

Reference resolution is effectively constant (~0.02–0.03 ms) and independent of vault size —
the conversation layer adds negligible overhead. A full turn tracks the query engine's
retrieval + ranking (≈68 ms for a broad query over 5,000 notes), which is near-linear.
`index_build` is a one-time construction cost (not per turn); a persisted index (deferred)
would remove it from interactive latency. No regressions: all 124 prior tests pass unchanged.

## Security

Read-only posture preserved and tested: the read-only safety test now also exercises
`jarvis chat`, hashing the fixture tree before/after and asserting no file changed or was
added/removed. No persistence, no logs, no network. Retrieved note text is treated as data,
never executed as instructions (Chat PRD req. 9): the conversation layer reads only
titles/relpaths/fields from the entity stack. Provider failures fail closed.

## Future recommendations

- Introduce a structured `ConversationQuery` (entities + intent + carried context) to
  replace the effective-query string shim before semantic retrieval (v0.6).
- Extract a `ProvenanceBuilder` so taxonomy rules are individually testable.
- When a real streaming provider lands, drive `StreamEvent` deltas from the provider stream.
- Feed session turns into a future proposal-based memory release as *candidates*, without changing
  this layer's read-only stance.

## Lessons learned

- Isolating conversation state from retrieval kept the deterministic query core untouched
  and made every new capability independently testable — the ADR-0012 layering paid off.
- Making every resolution choice an explicit `assumption` turned pronoun handling from a
  hidden risk into a visible, auditable step; provenance is most valuable exactly where the
  system had to guess.
- An overly-eager ambiguity heuristic (flagging any multi-entity memory) produced noise;
  tying ambiguity to *unrelated* topics (no shared title token) made the signal meaningful.

## Engineering Review — five questions

1. **Architectural assumptions.** Conversation is a thin layer over v0.3; session state is
   in-memory only; retrieval stays lexical and deterministic; providers remain behind the
   abstraction; retrieved text is data, not instructions.
2. **Technical debt introduced.** Effective-query string shim; heuristics concentrated in
   `_build_statements`; `ask_stream` re-chunks rather than streaming from the provider.
3. **Refactor before next major release.** Structured conversation query; `ProvenanceBuilder`
   extraction; provider-native streaming.
4. **Work intentionally deferred.** Persistent memory, conversation logs, cloud/Ollama
   adapters, semantic follow-up understanding, cross-process resume.
5. **If starting over.** Model the turn as a structured query object from the start (not a
   string), so reference resolution and future semantic retrieval share one representation.
