## Disposition

**Do not merge, cherry-pick, rebase, rename, or treat the historical candidate as v0.5
evidence.** It is a useful design spike whose narrow algorithms and lessons may inform a
fresh implementation against released main. Its contracts predate v0.3.1 trust hardening
and v0.4 Project Resume, and its Quality disposition was **Not ready**.

The historical implementation changed 27 source/test/script/document paths relative to its
old base. A direct comparison with current main is misleading because the branch predates
the released trust and Project Resume work; any implementation review must use a future
fresh branch from the Product Owner-approved base.

## Historical Quality blockers

The 2026-07-27 Quality review found five blocking areas:

1. retrieval relevance presented as answer confidence;
2. citations lacking passage/locator/revision support;
3. off-by-one trace turn numbering;
4. progressive rendering misrepresented as provider streaming; and
5. incomplete release evidence, including a benchmark that did not run as documented.

Current planning resolves these at the contract level, not by assuming the old fixes:
ADR-0014/0016 are mandatory; public turns start at 1; streaming is excluded; and the new
acceptance matrix requires direct commands, raw samples, exact identities, current-source
validation, and real-provider boundary evidence.

## Security gaps relative to released main

The candidate does not demonstrate immutable authorization scope on every entry, excluded
source non-disclosure, current-byte citation validation, explicit egress approval, exact
provider destination, secret isolation, prompt-injection containment across actual context
bytes, cross-workspace isolation, safe rendering, telemetry/fallback denial, or
policy/currentness revalidation on retry. Its old read-only fixture hash is positive but
insufficient for these newer boundaries.

## Evidence applicability

No historical test pass, benchmark number, implementation report statement, or QA result is
reusable as acceptance evidence. The following may be reused only as design hypotheses or
test-case ideas:

- multi-turn exact and pronoun follow-ups;
- ambiguous focus warnings;
- reset/history behavior;
- provider failure;
- bounded session history;
- 100/500/1,000/5,000-note scale shapes; and
- before/after vault integrity comparison.

Each must be rerun on the future exact v0.5 candidate using the accepted matrix.

## Migration conclusion

There is no released conversation schema or supported transcript, so no data migration is
required or desirable. Historical serialized objects are rejected by default. Code reuse,
if later authorized, must be deliberate line-level porting with tests—not Git history
integration—and must not import the old `confidence`, citation, streaming, or scope shapes.

## Final candidate disposition

**Park indefinitely as a historical design spike.** Preserve the branch read-only for
traceability. Begin any future Engineering work only from a separately pinned current-main
base after Product Owner approval and Chief-of-Staff implementation authorization.
