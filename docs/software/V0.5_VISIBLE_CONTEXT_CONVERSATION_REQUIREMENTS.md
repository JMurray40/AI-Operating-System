## Objective

Deliver the smallest useful multi-turn conversation in which a user can inspect and remove
authorized evidence before a real provider receives it, and can distinguish supported
source claims from model-generated material. The release remains read-only with respect to
the vault and does not create durable memory.

## Recommended user-visible scope

v0.5 provides:

1. interactive and scripted CLI conversation;
2. a versioned in-process application API shared by the CLI and tests;
3. explicit workspace scope and optional exact project scope;
4. deterministic follow-up reference resolution with every assumption visible;
5. a pre-dispatch context manifest with source title, locator, selection reason,
   sensitivity, token estimate, revision identity, and exclusion control;
6. immutable context snapshots and explicit approval before remote egress;
7. a deterministic mock adapter and exactly one approved real provider adapter;
8. complete-response generation, cancellation, normalized failure, usage, latency, and
   cost reporting;
9. claim-level passage/revision citations, coverage, conflicts, limitations, and
   qualitative evidence assurance; and
10. redacted Trace Mode for request, turn, policy, retrieval, context, provider, validation,
    usage, timing, and terminal status events.

## Explicit non-goals

- provider-response streaming or simulated streaming;
- graphical, desktop, web, mobile, or voice UI;
- public HTTP service;
- durable transcript persistence, resume across processes, archive, search, export,
  deletion workflow, shared conversations, or provider-side memory;
- vault writes, memory proposals, attachments, multimodal input, tools, plugins, MCP,
  agents, automation, browsing, or live GitHub;
- semantic/vector retrieval or silent query rewriting;
- provider fallback, model comparison, or automatic provider selection;
- numeric answer confidence or model self-rating.

## Required behavior

### R1 — Session and surface

1. A session has a random, non-semantic session ID and ordered public turn numbers starting
   at 1. Request and attempt IDs are separate.
2. State exists only in process and is erased by reset or process termination.
3. The application API owns conversation behavior; the CLI is a renderer/orchestrator and
   does not call provider adapters directly.
4. Scripted operation cannot bypass context policy or approval. Mock/local no-egress runs
   may use an explicit policy-approved non-egress mode.

### R2 — Authorization and selection

1. Every prepare request requires an immutable `AuthorizationScope`, workspace identity,
   request ID, maximum sensitivity, and provider destination.
2. ADR-0015 filtering occurs before candidate generation and graph expansion.
3. Unknown or missing sensitivity, workspace, policy, destination, or grant fails closed.
4. An optional project selector uses ADR-0018 exact tiered identity. Conversation does not
   use relevance to guess a project.
5. Excluded sources cannot affect visible candidates, assumptions, conflicts, errors,
   timing detail, traces, or provider input except safe aggregate counts.

### R3 — Visible context and snapshot

1. `prepare` produces a complete user-visible manifest before remote dispatch.
2. Each context item includes stable source ID, current path/title, exact fingerprint,
   heading/line locator, bounded excerpt, retrieval reason, relative relevance when
   applicable, sensitivity, and deterministic token estimate.
3. Context selection and the complete provider prompt obey hard budgets that include all
   wrappers, roles, separators, instructions, history, citations, and output reserve.
4. Removing an item creates a new immutable snapshot and digest. No in-place mutation is
   permitted.
5. The manifest identifies omissions and truncation without disclosing excluded sources.
6. The snapshot binds prompt-template, prompt-assembler, history-serialization,
   token-estimator, safety-instruction, and output-reserve versions, plus the output-reserve
   value. Its digest covers those values with all other semantic inputs.

### R4 — Approval and provider egress

1. Remote dispatch requires explicit approval bound to snapshot digest, workspace,
   provider destination, model role, normalized user request, policy version, every bound
   prompt-construction version, output reserve, and expiry.
2. Authorization, egress policy, and current-byte citation validation run again immediately
   before prompt assembly and dispatch.
3. Prompt assembly cannot begin before those checks pass.
4. Every content-bearing request field is deterministically derived from the approved
   snapshot and its bound versions. The adapter may add only allowlisted transport metadata
   and opaque authorization transport; it may not add undeclared content, telemetry,
   fallback routing, redirects, or provider fields.
5. Provider credentials never enter content-bearing payloads, prompts, traces, errors,
   session objects, or source control. Network destinations are allowlisted; telemetry,
   provider memory, tools, and fallback routing are disabled.

### R5 — Conversation and retry semantics

1. Reference resolution is a deterministic function of visible session state. A resolved
   pronoun or ellipsis is shown as an assumption before approval.
2. Ambiguity is surfaced; dangerous or materially ambiguous identity is not guessed.
3. An exact retry reuses the same request and snapshot digest but creates a new attempt ID.
4. Current-byte or policy drift blocks retry and requires a fresh prepare/approval cycle.
5. Changed user input, context, provider, model role, or workspace creates a new request.

### R6 — Generated answers and evidence

1. Every material source-derived claim has one or more citations satisfying ADR-0016 and
   validating against current bytes immediately before emission.
2. Metadata-derived claims cite the exact validated metadata passage or deterministic
   metadata locator and fingerprint.
3. A claim is typed as `fact`, `inference`, `model_knowledge`, `unknown`, or `assumption`.
   Inference cites every material premise. Model knowledge is visibly not vault-supported.
4. Unsupported source claims cannot be presented as supported. Empty excerpts and `0-0`
   locators are invalid passage citations.
5. Answer coverage is `complete`, `partial`, `incomplete`, or `none`, with explicit
   limitations and conflicts. An incomplete-only answer is not fully evidence-backed.
6. Retrieval `relative_relevance` remains separate from qualitative answer assurance. No
   numeric answer confidence is emitted.

### R7 — Untrusted content and rendering

1. Vault text, user text, repository content, and provider output
   are untrusted data and cannot grant authority or alter system instructions.
2. Context is structurally delimited and labeled with source boundaries.
3. Provider Markdown is sanitized: no active HTML, scripts, remote images, data URLs, or
   automatic link activation. Raw provider payloads are never rendered.
4. Prompt-injection warnings are advisory; enforcement does not depend on detection.

### R8 — Terminal states, cancellation, and degradation

1. Attempts terminate exactly once as `completed`, `failed`, `cancelled`, or `blocked`.
2. Cancellation reaches the adapter within a bounded time and never creates a completed
   message or automatic retry.
3. Provider timeout, malformed output, network denial, policy denial, citation validation
   failure, and budget failure are distinct redacted outcomes.
4. No provider or network produces a useful prepare/context-inspection path. Dispatch is
   unavailable with an actionable limitation.
5. Unknown usage or cost is displayed as unknown, not zero. Estimates and provider-reported
   values are labeled separately with currency and units.

### R9 — Trace and privacy

1. Public turn numbering is one-based and consistent across text, JSON, trace, and tests.
2. Trace records observable events, not chain-of-thought.
3. Trace excludes message bodies, context excerpts, secrets, raw provider payloads, absolute
   private paths, excluded identities, and raw errors by default.
4. Trace includes contract/policy/provider-adapter versions, safe snapshot digest, counts,
   budgets, timings, usage, cost status, validation outcomes, and terminal state.
5. Logs and crash diagnostics use the same redaction contract and are not conversation
   persistence.

### R10 — Read-only and compatibility

1. No vault, pilot, Git repository, provider memory, or canonical note is modified.
2. No operational conversation store is created in v0.5.
3. The historical candidate has no migration authority. No historical serialized contract
   or transcript is accepted by default.
4. Any compatibility reader must be explicitly authorized, shape-strict, bounded to one
   version, and unable to reinterpret historical `confidence` as answer confidence.
5. Existing query and Project Resume interfaces retain their released behavior.

## Non-functional requirements

- Deterministic prepare output for identical bytes, scope, policy, request, configuration,
  evaluation time, and destination.
- Prepare p95 under 2 seconds at 5,000 synthetic notes on the accepted v0.4 reference
  machine; no more than 20% regression in unchanged query stages from their accepted
  equivalent baseline.
- Application overhead excluding retrieval and external provider time p95 under 250 ms.
- Cancellation acknowledgment p95 under 500 ms after adapter receipt in controlled tests.
- Hard input/context/prompt/output/time/memory limits, with p50/p95/p99 and peak memory
  reported at 100/500/1,000/5,000 notes.
- CLI keyboard-only operation, non-color equivalents, stable screen-reader labels, no
  information conveyed by color alone, and no continuous dynamic output because streaming
  is excluded.
- Clean install, installed-command check, offline fixture path, uninstall/reinstall,
  missing/corrupt derived-state recovery, and no canonical-source repair.

## Product Owner decisions required

1. Approve session-only state and defer persistence lifecycle features.
2. Approve CLI plus in-process API and defer graphical/public-network surfaces.
3. Select the one real provider and approve its endpoint, data-use terms, credential
   boundary, model role, and test budget.
4. Approve non-streaming v0.5.
5. Decide the roadmap collision: recommended v0.5 Conversation and Proposed Memory v0.6,
   which requires moving current v0.6 Semantic Search; or approve another sequence.

No requirement in this document authorizes implementation.
